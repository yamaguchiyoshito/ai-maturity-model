# 文書改善計画：AIを含む開発に不慣れな読者が順に読んで理解できる構成へ

作成日：2026-10-04　状態：計画（未着手）。判定基準の正本（`criteria/`）は変更しない。

## 1. 目標

- 読者像を「SI受託開発の経験はあるが、AIエージェント・Agent Skill・共有CIなどに不慣れな人（PM・PL・リーダー、評価担当者）」に置く。
- ツールや基準の前に、「AIを含む開発とは何か」「なぜ測るのか」「モデルの3つの概念」を説明してから本文へ入る。
- サイドバーの上から順に読めば理解できる一本の順路にする。前後ページのリンク（VitePressの prev/next）はこの順路に従う。
- 用語は初出で一文で説明し、用語集へリンクする。用語集を「後で引く場所」から「どこからでも戻れる場所」に変える。

## 2. 現状の診断（通読して分かった障害）

| # | 障害 | 具体例 |
|---|---|---|
| D1 | 前提の説明がない | 「AIが環境に接続する」「Skillを版管理する」が、AIエージェントが何をするか（ファイルを読む・書く・コマンドを実行する）を知らない読者には像を結ばない。Skillが「ファイルに書いた手順書」であることもどこにも書いていない |
| D2 | 用語が定義より先に出る | ホームの早見表に MR、共有環境、イベント・スケジュール起動、ベースライン、統制範囲が未説明で登場。用語集は付録（最後） |
| D3 | 読む順が目的別で、通読の順路がない | ホームは「読者別の入口」の表のみ。はじめての読者がどこから読むかの指示がない |
| D4 | 「なぜ」が付録にある | `appendix/background.md` が最も理解の入口に近い内容だが、ナビの最後 |
| D5 | 評価の手順より先に判定基準が並ぶ | ナビ順が モデル → 軸別チェックリスト → 工程別チェックリスト → 効果 → 評価する。基準ID（`SK-2-04` など）の表が、使い方を知る前に現れる |
| D6 | 抽象名詞の表が中心で、具体像がない | レベル別ビューは「制度化」「テーラリング」「ベースライン」の表。各レベルのPJがどんな一日を過ごしているかの例がない |
| D7 | 生成ページに前置きがない | 工程別・軸別チェックリストは、タグや【ローカル事前検証】の意味、確認元の読み方をページ内で説明していない（索引ページにだけある） |
| D8 | 評価の進め方がSkill前提 | `assess/howto.md` の手順1がSkill。手作業で確認する読者の流れが脚注扱い |
| D9 | 報告書の例が長く、読み方がない | 1,200語の生成物に前置きがなく、初学者には「何を見ればよいか」が分からない |
| D10 | 契約・収支の前提が未説明 | 請負と準委任で削減効果の帰属が変わる話は重要だが、契約形態の説明がない |

## 3. 新しい構成案（ナビ順＝読む順）

```text
1 ホーム              目的、読む順（はじめての方／評価担当／効果測定担当）、早見表は後半へ
2 はじめに（新設 guide/）
  2.1 AIを含む開発とは     AIアシスタント／エージェントが行うこと、人の役割、
                           「AIを使う」の4つの姿（チャットに貼る → ローカルで実行 → 共有環境に接続 → 自動起動）
  2.2 開発の基本用語        リポジトリ、コミット、MR・PR、Issue、CI、ブランチ保護、WBS、工数、請負と準委任
  2.3 なぜ成熟度を測るのか  現 appendix/background.md を移動し、架空PJの事例（実装だけ速くなりレビュー待ちが増える）を加筆
  2.4 モデルの全体像        レベル・評価軸・自動化段階の3概念を1ページで。架空PJ「〇〇システム」をレベル1→2→3で追う
3 モデル              現行4ページ。各ページ冒頭に「前提となる用語」行、各レベルに「このPJの一日」の例を追加
4 評価する            手順を基準より先に置く。手作業の流れを主、Skillは補助。報告書の例に読み方を前置き
5 軸別チェックリスト   判定基準の参照先。生成ページに前置き（確認元・IDの読み方・用語リンク）
6 工程別チェックリスト 同上（タグの意味を各ページにも）
7 効果を測る          算定式の前に「基準工数とは」「なぜ単純平均しないか」の説明を追加
8 付録                CMMIとの対応、用語集（拡充）、改訂履歴
```

変更点は三つ。「はじめに」を新設し、「背景」をそこへ移す。「評価する」をチェックリストの前に出す。各ページに前提用語の行と次に読むページを付ける。

## 5. 横断ルール（書き方の約束）

1. 用語は初出で一文の説明を付け、以後は用語集へリンクする。カタカナ語と略語（MR・PR、CI、WBS）は初出で正式名称を添える。
2. 表の前に、その表が何を比べているかを一文で書く。表だけの節を作らない。
3. 各レベル・各段階に、架空PJの具体例を一つ付ける。例は「誰が・何を・どこで・何を記録するか」の形にそろえる。
4. 「ツール名」より先に「行為」を書く（例：「AIがテストを実行する」→ 次に「Claude Code などのエージェントで」）。
5. 読者が実際に行う操作は番号付き手順にし、必要な権限・所要時間・成果物を添える。
6. 1ページは1,000語以内を目安にし、超える場合は分割する（報告書の例は除く）。

## 7. 着手前に決めたい点

| 論点 | 案 | 影響 |
|---|---|---|
| 主な読者 | PM・PL・評価担当者を主、開発者を従 | 2.1〜2.2 の深さ（git操作の説明まで含めるか） |
| 「評価する」の位置 | チェックリストの前（手順 → 基準） | 現行の「基準 → 手順」から変わる。ホームの入口表も合わせる |
| 効果の目安 | 初学者向けには「仮説値」の注意を強め、数表は折りたたまず残す | 公開範囲の判断（README の確認事項）と連動 |
| 架空PJの例 | 一つのPJ「〇〇システム」をレベル1→3で追う通し事例 | 全ページで同じ例を使うため、先に設定（契約形態、体制、工程）を決める |
| 用語の表記 | 「MR・PR」は「変更の提案（MR・PR）」のように行為を先に置く | 基準の文言は変えないため、ページ側と基準側で表記が異なる箇所が出る |
