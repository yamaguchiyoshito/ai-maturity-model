# 成熟度モデルの全体像

このページでは、本成熟度モデルを構成する三つの概念と、その関係を説明します。ここを読めば、以降の[成熟度モデル](../model/index.md)の各ページを、どの概念の話をしているかを意識しながら読めます。

## 三つの概念

| 概念 | 答える問い | 値 |
|---|---|---|
| 制度化レベル | その仕組みは、どこまで再現できるか。本人だけか、PJ内か、他のPJでもか | 未到達、レベル1〜5 |
| 評価軸 | 何を見るか | 5つの軸 |
| 自動化段階 | AIはどこまで人手を介さずに動いているか | A1〜A4 |

PJの状態は「レベル2／A2」のように、**制度化レベルと自動化段階の組**で表します。レベルは5つの評価軸それぞれに付き、PJのレベルはその最小値です。

## 制度化レベル：どこまで再現できるか

レベルは、CMMIという成熟度モデルのレベル構成を参考にした5段階です。要点は「同じ結果を、誰が、どの範囲で出せるか」です。

| レベル | 名称 | 再現できる範囲 | 具体例（架空PJ） |
|---|---|---|---|
| 未到達 | — | 再現できない | AIを使っていない、または試しに使っただけ |
| 1 | 属人的 | 本人 | 開発者2名がそれぞれのやり方でAIを使っている。他の人は同じ結果を出せない |
| 2 | プロセス確立 | PJ内 | PJ共通のSkillと権限設定があり、5名の誰が使っても同じ手順で同じ形の成果物が出る。工数を記録している |
| 3 | 組織標準化 | 他のPJ | 組織の標準Skillと接続キットから始め、PJ固有の調整と理由を記録している。他のPJと実績を比べられる |
| 4 | 定量管理 | 予測できる | 複数PJの実績から「通常の範囲」が分かっており、外れたら数値で検知できる |
| 5 | 継続的最適化 | 改善し続ける | 実績が標準を書き換え続ける。AIが改善案を出し、人が承認する |

レベル4と5は、複数のPJの実績が必要なため、PJ単独では到達できません。組織側の整備が条件です。

## 評価軸：何を見るか

| 軸 | 確認する問い | 販売管理PJの出発点 |
|---|---|---|
| Agent Skill | AIが何を、どの手順と判断基準で行うかが定義されているか | 1名が個人用の手順書を持っている |
| 環境との接続 | AIが必要な情報を取得し、作業と検証を実行できるか | 手元のPCの中だけ。共有リポジトリへの権限は個人のもの |
| 開発標準資産 | AIと人が何に準拠して設計・実装するかが具体化されているか | 方式設計書はあるが、実装例と対応していない |
| AI前提の開発プロセス | 工程と人の役割が、AIの実行を前提に設計されているか | WBSは従来のまま。レビュー容量を考えていない |
| AI前提の見積もり・PJ収支 | AIの効果と費用が見積もりと収支に反映され、実績で検証されているか | 従来の人月見積もり。AI利用料は原価に入っていない |

前の3軸はAIが使う「資産と能力」、後の2軸はそれを前提にPJを運営する「管理プロセス」です。販売管理PJの問題（レビュー待ち、効果を説明できない）は、後の2軸に現れています。

## 自動化段階：AIはどこまで自分で動くか

[AIを含む開発とは](ai-development.md)で説明した「四つの姿」が、そのまま自動化段階です。

| 段階 | 姿 |
|---|---|
| A1 | 手元で動かす。人が起動し、自分のPCで実行・確認する |
| A2 | 共有の場につなぐ。共有リポジトリ・Issue・共有CIに接続し、変更の提案（MR・PR）まで作る |
| A3 | 自動で起動する。出来事や時刻を合図に、サーバ上で実行・検証・記録する |
| A4 | 自分で判断して繰り返す。決められた範囲でSkillと環境を選び、自律的に反復する |

## 三つの原則と、その理由

| 原則 | 理由 |
|---|---|
| PJのレベルは5軸の最小値 | 1軸だけ高くても、低い軸がPJ全体の制約になる。販売管理PJでSkillの軸だけ上げても、レビュー容量を計画しなければ待ちは減らない |
| 自動化はレベルの範囲内で進める | 止める仕組みと権限と記録がないまま無人で動くものは、事故が起きたときに原因も範囲も分からない |
| 証拠で判定する | 「使っています」という自己申告では、状態を比較できない。リポジトリ、実行記録、設定、文書で確認する |

## 販売管理PJをレベル1から3まで追う

| レベル | PJの状態 | 何を変えたか |
|---|---|---|
| 1 | 開発者2名が個人のやり方でAIを使う。効果は本人の体感だけ | — |
| 2 | 入力チェック生成のSkillをPJ共通にし、リポジトリで版管理。AIに許す操作と人の承認が要る操作を設定で定義。WBSに「AI生成」「人の確認」「受入基準」を追加。基準工数を記録し、AI利用料を原価に計上 | 1名の手順書をチームの手順書にした。レビュー容量に合わせて生成量を計画した。効果を測る分母を作った |
| 3 | 組織標準のSkillと接続キットに切り替え、PJ固有の変更と理由を記録。方式設計の制約をCIで自動検証。組織の見積もりモデルと、請負契約での効果の帰属ルールを適用 | PJの作り方を組織の作り方に合わせ、差分だけを説明すればよい状態にした。他のPJと実績を比べられるようにした |

レベル2になった時点で、PJは「誰がやっても同じ結果」と「効果の測定」を手に入れます。レベル3では、それが組織の他のPJと比較できるようになります。

## 評価の流れ

評価は、次の流れで進めます。詳しい手順は[評価の進め方](../assess/howto.md)にあります。

1. 証拠を集める。リポジトリ、設定、文書、実行記録を確認する。リポジトリの走査はSkillで自動化できる。
2. [軸別チェックリスト](../checklist/index.md)の基準と照合し、軸ごとのレベルと自動化段階を決める。
3. PJのレベル（5軸の最小値）と、統制不足の有無を確認する。
4. [工程別チェックリスト](../process/index.md)で、工程ごとの偏りを見る。
5. 制約になっている軸と工程を特定し、次のレベルへの施策を決める。
6. 四半期ごと、または主要な工程の終了時に再評価する。
