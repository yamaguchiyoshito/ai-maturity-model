# AIを含む開発とは

**前提となる用語：** このページは用語の前提を置きません。開発用語は次の[開発の基本用語](terms.md)で説明します。

このページでは、「AIを使って開発する」と言うときに実際に何が起きているのかを、ツール名や基準より先に説明します。本モデルの評価軸である **Agent Skill**、**環境との接続**、**開発標準資産** が、それぞれどんな具体物を指すのかが分かることを目標にします。

## チャットに貼る使い方と、エージェントに任せる使い方

生成AIの開発利用には、大きく二つの形があります。

| 形 | 何が起きるか | 人が行うこと |
|---|---|---|
| チャット型 | 人がブラウザの画面にコードや質問を貼り、AIが回答を返す | 貼る、読む、必要な部分を自分の環境へ写す |
| エージェント型 | AIが開発者の作業環境の中で、ファイルを読み、書き換え、コマンドを実行し、結果を見て次の行動を決める | 目的を指示する、結果を確認する、承認する |

本モデルが主な対象とするのは、エージェント型です。Claude Code や GitHub Copilot のコーディングエージェントのように、端末やリポジトリの中で動くプログラムを指します。本モデルでは、この種のプログラムを「AI」または「AIエージェント」と呼びます。

## AIエージェントが行う四つの行為

エージェント型のAIが行うことは、次の四つに整理できます。この四つは、後で説明する「環境との接続」の軸がそのまま評価の対象にしています。

| 行為 | 具体例 | 人がやっていた場合との違い |
|---|---|---|
| 読む | ソースコード、設計書、Issue、エラーログを開いて内容を把握する | 人が貼り付けなくても、AIが自分で必要なファイルを探す |
| 書く | ファイルを新規作成する、既存のコードを修正する、コミットを作る | 変更がそのまま作業環境に反映される |
| 実行する | ビルド、静的解析、テスト、スクリプトを走らせる | 自分の変更が動くかどうかを、AIが自分で確かめられる |
| 記録する | 実行結果、変更理由、確認した内容を、コミットやMR・PRや報告に残す | 後から人が追跡できる形で証跡が残る |

**人の役割はなくなりません。** 目的を決めること、AIに何をしてよいか（権限）を与えること、結果を確認して受け入れるか判断すること、問題があれば止めることは、人の仕事として残ります。本モデルの上位レベルは「人が不要になる状態」ではなく、「人の役割が確認と承認と例外判断に移り、それが設計されている状態」を指します。

## 「AIを使う」の四つの姿

同じ「AIを使っている」でも、どこで、誰が起動して、どこまで影響が及ぶかはまったく違います。本モデルはこれを **自動化段階（A1〜A4）** として区別します。

| 姿 | 何が起きているか | 起動する人 | 影響が及ぶ範囲 | 本モデルでの呼び方 |
|---|---|---|---|---|
| 手元で動かす | 開発者が自分のPCでAIを起動し、ファイル変更とテスト実行をさせ、結果を自分で確認する | 本人 | 本人のPCの中 | A1 |
| 共有の場につなぐ | AIがチームの共有リポジトリやIssueを読み書きし、変更の提案（MR・PR）まで作る。取り込むかどうかは人がレビューして決める | 本人 | チームの共有環境。ただし取り込みは人が判断 | A2 |
| 自動で起動する | Issueの起票やスケジュールを合図に、サーバ上でAIが起動し、実行・検証・記録まで行う | 人ではなく、出来事や時刻 | 無人で共有環境に変更が生じうる | A3 |
| 自分で判断して繰り返す | 決められた範囲の中で、AIがどの手順書を使うか選び、実行と修正を繰り返し、異常なら止まる | 人ではなく、AI自身 | 範囲内で自律的に反復 | A4 |

販売管理PJの出発点は「手元で動かす」です。開発者2名が自分のPCでAIにコードを書かせ、テストを回し、問題なければ自分でコミットしています。

姿が進むほど効果は大きくなりますが、影響の範囲も広がります。無人で動くものには、止める仕組み、権限の制限、記録が先に必要です。本モデルが「レベルより先に自動化を進めてはいけない」と言うのは、このためです。

## Agent Skillとは：ファイルに書いた手順書

**Agent Skill**（以下「Skill」）は、AIエージェントに繰り返し行わせたい作業の手順を、ファイルに書いて保存したものです。中身は人が読める文章で、おおむね次の項目を持ちます。

```text
目的　　　：この手順書が何をするためのものか
入力　　　：AIが最初に読むべきもの（設計書、対象ディレクトリなど）
手順　　　：何を、どの順で行うか
判断基準　：どうなったら完了か、どういう場合は人に確認するか
出力　　　：成果物の形式（ファイル名、見出し構成、報告の書式）
```

毎回チャットに打ち込む指示（プロンプト）との違いは、**保存されて再利用される**ことです。保存されているので、他の人も同じ結果を出せます。ファイルなので、変更を他の人がレビューできます。リポジトリに置けば、いつ誰が何を変えたかを履歴で追えます。

販売管理PJでは、開発者の1人が「画面の入力チェック処理を、設計書の項目定義から生成する」手順を自分用に書いて保存しました。これが個人のSkillです。本人は毎回同じ品質で生成できますが、他の開発者はその存在を知りません。この状態を本モデルはレベル1と呼びます。チーム全員が同じSkillを使い、変更をレビューし、出力を確認する手順が決まった状態がレベル2です。

## 環境との接続とは：AIが読み書きできる範囲

**環境との接続**は、AIがどこまでの情報に触れ、どこまでの操作をしてよいかを指します。

| 接続の範囲 | AIができること |
|---|---|
| 手元のPCだけ | 自分のPCにあるファイルを読み書きし、ビルドやテストを実行する |
| 共有リポジトリ | チームのコードを取得し、変更の提案（MR・PR）を作る |
| Issue | 課題の内容を読み、作業結果をコメントで記録する |
| 共有CI | 共有環境での自動検証（ビルド、テスト）の結果を取得する |
| 本番に近い環境 | テスト環境の操作、ログの取得 |

接続を広げるときに決めなければならないのは、**権限**と**承認**です。AIにどの操作を許すか、どの操作は人の承認がなければ実行できないか（例：共有ブランチへの取り込み、本番環境への変更）を、設定として定めます。本モデルの「環境との接続」軸のレベル2は、この権限と承認が定義されている状態を指します。

## 開発標準資産とは：AIが判断しなくてよいことを決めておくもの

**開発標準資産**は、標準フレームワーク、テンプレートリポジトリ、方式設計の三つをまとめた呼び方です。

| 資産 | 何か | なぜAI利用で重要か |
|---|---|---|
| 標準フレームワーク | 採用する技術と、その標準的な使い方（設定、共通部品、利用ガイド） | AIが「どのライブラリでどう書くか」を毎回判断せずに済む |
| テンプレートリポジトリ | ディレクトリ構成、ビルド・テスト・CIの設定、代表機能の実装例が入った、動く状態の雛形 | AIが最初から動く構成の上で作業でき、生成物の形がそろう |
| 方式設計 | 認証、例外処理、ログ、データアクセス、トランザクションなどの共通方針と、その実装例 | AIが方式を勝手に決めない。人のレビューも方針との差分だけを見ればよくなる |

AIは判断材料がなければ、その場で妥当に見える方式を選びます。10人の開発者がそれぞれAIを使えば、10通りの例外処理やログ出力が生まれます。標準資産は、人にとっても必要なものでしたが、AIが生成量を増やすほど、その有無の差が大きくなります。

## このページのまとめ

- 本モデルが対象とするのは、作業環境の中でファイルを読み、書き、実行し、記録するエージェント型のAI利用です。
- AIの使い方には、手元で動かす、共有の場につなぐ、自動で起動する、自分で判断して繰り返す、の四つの姿があり、本モデルは自動化段階A1〜A4として区別します。
- Agent Skillはファイルに書いた手順書、環境との接続はAIが読み書きできる範囲と権限、開発標準資産はAIが判断しなくてよいことを決めておく土台です。
