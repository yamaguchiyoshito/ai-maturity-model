# 開発の基本用語

本モデルの説明には、開発と契約の用語が繰り返し出てきます。このページでは、それらを五つのまとまりに分けて、意味と「本モデルのどこで使うか」を示します。すべてを覚える必要はありません。後のページで分からない言葉が出たら、ここか[用語集](../appendix/glossary.md)に戻ってください。

## 変更と履歴

| 用語 | 意味 | 本モデルでの使われ方 |
|---|---|---|
| リポジトリ | ソースコード、設定、文書を、変更履歴ごと保管する場所。Gitという仕組みで管理するのが一般的 | 評価の証拠の多くはリポジトリの中にある。評価下書きを作るSkillはリポジトリを走査する |
| コミット | リポジトリへの変更を、理由（メッセージ）とともに記録する単位 | AIが変更を記録した証拠。誰が、いつ、何を変えたかが残る |
| ブランチ | 本線のコードに影響を与えずに変更を進めるための、作業用の分かれ道 | AIの作業は通常、作業ブランチで行う |
| MR・PR | マージリクエスト、プルリクエスト。作業ブランチの変更を本線へ取り込みたいという**変更の提案**。レビューの単位になる | AIが「MRまで作る」とは、変更の提案までを行い、取り込みは人が判断する状態 |
| レビュー | 変更の提案を、別の人が読み、指摘し、取り込んでよいか判断すること | AIの生成量が増えると、レビューがPJの制約になりやすい |
| マージ | 変更の提案を本線へ取り込むこと | 人の承認なしにマージさせるかどうかが、権限設計の要点 |
| ブランチ保護 | 本線のブランチに対して、「レビュー承認がなければマージできない」「必須の自動検証に合格しなければマージできない」といった規則を、共有環境の設定で強制する仕組み | レベル3の「停止条件が共有環境の設定で強制される」の具体物 |

## 作業の管理

| 用語 | 意味 | 本モデルでの使われ方 |
|---|---|---|
| Issue | 課題、要望、作業項目を一件ずつ記録する票。リポジトリと同じ場所で管理することが多い | AIがIssueを読んで作業を始め、結果をIssueに記録する |
| WBS | 作業分解構成。PJの作業を工程と作業項目に分解して並べた一覧。見積もりと進捗管理の土台 | 「WBSにAI適用作業と人の確認点がある」がレベル2の条件 |
| 工数 | 作業にかかる人の時間。人日、人月で数える | 効果は工数の差で測る |
| 基準工数 | AIを使わなかった場合に、その作業にかかると見込まれる工数 | 効果算定の分母。これを記録していないPJは効果を測れない |
| 完了条件・受入基準 | 作業や成果物を「できた」とみなす条件 | AIの生成物を受け入れる基準が決まっているかを評価する |
| 工程 | 要件整理、外部設計、詳細設計、実装、単体テスト、結合・システムテストなど、開発の段階 | 工程別チェックリストの単位。制約工程を見つける |

## 自動検証

| 用語 | 意味 | 本モデルでの使われ方 |
|---|---|---|
| ビルド | ソースコードから動くプログラムを組み立てること。失敗すれば、少なくとも文法や依存関係に問題がある | AIが自分の変更を確かめる最初の手段 |
| 静的解析 | プログラムを動かさずに、コードの問題（規約違反、危険な書き方）を機械的に検出すること | 方式設計の制約を自動で検証する手段の一つ |
| 単体テスト | 関数やクラスなど小さな単位ごとに、期待どおり動くかを確かめる自動テスト | AIが生成したコードの正しさを、AI自身が確かめる手段 |
| ローカル事前検証 | 共有する前に、個人の作業環境でビルド、静的解析、テストを実行すること | レベル1の「AIが作業中の変更に対して検証を実行できる」の具体物 |
| CI・共有CI | 継続的インテグレーション。コミットや変更の提案を合図に、共有環境で自動的にビルドとテストを実行する仕組み。「共有CI」はチームで共有しているCI環境を指す | A2・A3の接続先。実行記録が証拠になる |
| 必須ジョブ | 共有CIのうち、合格しなければマージできないと定めた検証 | ブランチ保護と組み合わせて、停止条件を強制する |

## 契約と収支

SI受託開発では、契約の形によって「工数が減ったときに誰が得をするか」が変わります。本モデルの見積もり・PJ収支の軸は、ここを避けて通れません。

| 用語 | 意味 | 本モデルでの使われ方 |
|---|---|---|
| 請負 | 成果物の完成に対して対価を受け取る契約。工数が減れば、受注側の利益が増える | 削減効果は利益になる。ただし次回以降の見積もりへの反映を顧客から求められうる |
| 準委任 | 作業時間や体制の提供に対して対価を受け取る契約。工数が減れば、そのまま売上が減る | 削減した時間を何に充てるか（品質、範囲拡大、価格）を決めないと、成熟度が上がるほど収支が悪化する |
| 人月 | 1人が1か月働く量を単位にした見積もりと価格の方式 | AI利用で「作業量と価格の関係」が崩れるため、レベル5では人月以外の価格方式の検証を求める |
| PJ原価 | PJにかかる費用。人件費に加えて、AIの利用料、基盤の費用も含まれる | AI利用料を原価に入れていない状態はレベル1 |
| 帰属ルール | 削減された工数や費用を、価格の値下げ、利益、品質への再投資のどれに充てるかの取り決め | レベル3の要点。契約形態別に定める |

## 標準と方式

| 用語 | 意味 | 本モデルでの使われ方 |
|---|---|---|
| フレームワーク | アプリケーションの骨組みを提供するソフトウェア部品の集まり（例：Spring Boot、React） | 標準フレームワークは開発標準資産の一つ |
| テンプレートリポジトリ | 新しいPJやモジュールを始めるときの雛形として配布する、動く状態のリポジトリ | 開発標準資産の一つ。「同じリリース版から開始できる」がレベル2 |
| 方式設計 | 認証、例外処理、ログ、データアクセスなど、システム全体に共通する作り方の方針を定めた設計 | 文書だけでなく、実装例と検証方法に対応していることを求める |
| ADR | 設計判断の記録。何を、なぜそう決めたかを一件ずつ残す文書 | 標準からの逸脱と理由を記録した証拠になる |
| テーラリング | 組織の標準を、PJの条件に合わせて調整すること | レベル3では、調整した差分と理由を記録していることを求める |
| ベースライン | 複数PJの実績から求めた「通常の範囲」。たとえばCIの初回成功率が通常は何％か | レベル4の前提。これがないと「異常」を数値で定義できない |
