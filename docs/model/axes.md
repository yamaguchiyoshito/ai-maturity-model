# 軸別ビュー

各軸がレベルごとにどう変わるかを読むためのページです。「この軸で次に何を整備するか」を決めるときに使います。判定に使う基準は[軸別チェックリスト](../checklist/index.md)にあります。

## Agent Skill

組織固有の手順、判断基準、品質基準、成果物形式を、AIが再利用できる状態になっているかを評価します。

平たく言えば、「AIにやらせる作業の手順書が、誰のものとして、どこに保存され、どう保守されているか」を見る軸です。手順書が個人の頭の中や個人のPCにしかなければレベル1、PJのリポジトリにあって変更がレビューされていればレベル2、組織が配布したものから始めていればレベル3です。

| レベル | 状態 |
|---|---|
| 未到達 | Skillなし。都度プロンプトを入力している |
| 1 | 個人が作成したSkillを本人が反復利用している |
| 2 | PJ共通のSkillを版管理し、変更をレビューし、出力を検証している。管理責任者と利用手順があり、適用作業の工数を記録している |
| 3 | 組織共通のSkillを複数PJが利用している。品質・セキュリティ基準を内蔵し、Skill間で出力を受け渡す。PJの改変と理由を記録している |
| 4 | Skill別に品質効果・生産性効果・運用コストのベースラインを持ち、閾値を外れたSkillを検知している |
| 5 | 失敗事例と実行履歴からSkillの不足を特定し、AIが修正案を作成、人間がレビューして標準へ反映している |

## 環境との接続

AIが開発・業務環境から情報を取得し、変更、実行、検証、記録まで行えるかを評価します。この軸には[自動化段階](automation.md)を併記します。

平たく言えば、「AIがどこまで読み書きでき、どの操作に人の承認が要るかが決まっているか」を見る軸です。接続の範囲が広がるほど効果は大きくなりますが、権限と承認と停止条件の定義が先に必要です。

| レベル | 状態 |
|---|---|
| 未到達 | AIが環境に接続していない。人がコピーと転記を行っている |
| 1 | 個人のローカル環境で、ファイル変更、コミット、ビルド・テスト実行、結果取得ができる |
| 2 | PJの共有リポジトリ、Issue、共有CIに接続している。AIの権限と人間の承認が必要な操作を定義済み。検証コマンドと必須ジョブがPJ共通 |
| 3 | 組織標準の接続キット（権限、CI定義、エージェント実行基盤）を適用している。マージ停止条件と証跡保存が共有環境の設定で強制される |
| 4 | CI初回成功率、再試行回数、待ち時間の管理限界を定義し、停止条件・再試行条件・人間への確認条件を数値で設定している |
| 5 | 実行履歴から接続・権限・起動条件を改善し、複数PJへ展開している |

## 開発標準資産

標準フレームワーク、テンプレートリポジトリ、方式設計が整備され、設計・実装・検証の共通の土台として再利用できるかを評価します。

平たく言えば、「AIと人が判断しなくてよいことが、動く形で決まっているか」を見る軸です。方式設計書があっても、それに対応する実装例と検証方法がなければ、AIは文書を読んでも同じ方式で書けるとは限りません。

| 評価対象 | 整備する内容 | 確認する証拠 |
|---|---|---|
| 標準フレームワーク | 採用技術と対応バージョン、標準設定、共通部品、利用方法、拡張方法、適用条件 | 依存関係定義、設定ファイル、共通部品、利用ガイド、動作する実装例 |
| テンプレートリポジトリ | ディレクトリ構成、環境構築手順、ビルド・起動・テスト・静的解析・CIの設定、代表機能の実装例 | 配布元、リリース版、README、実行コマンド、代表機能とテストの実行結果 |
| 方式設計 | レイヤーの責務と依存方向、認証・認可、例外処理、ログ、データアクセス、トランザクション、外部接続、非機能要件、例外を認める条件 | 方式設計書、設計判断の記録、方式と実装例・検証方法の対応表、例外の承認記録 |

フレームワークは自社開発である必要はありません。方式設計は、文書があるだけでは整備済みとしません。実装例と検証方法に対応していることを確認します。

| レベル | 状態 |
|---|---|
| 未到達 | 動作する構成が保存されていない |
| 1 | 動作する最小構成と起動・テスト手順を個人が保存している |
| 2 | PJのフレームワーク、テンプレートリポジトリ、方式設計を定義し、複数メンバーが同じリリース版から開始できる |
| 3 | 組織標準資産の採用版・個別変更・例外・承認理由を記録している。方式設計から実装例と検証方法をたどれ、自動判定できる制約はCIで検証している |
| 4 | 標準資産への適合率、逸脱件数、更新適用のリードタイムを測定し、目標値で管理している |
| 5 | 複数PJの実績から標準資産を改善し、互換性検証、配布、PJ側の更新まで継続している |

## AI前提の開発プロセス

工程定義、WBS、役割、品質ゲート、工程間の受け渡しが、AIの実行を前提に設計されているかを評価します。

平たく言えば、「PJの計画が、AIが生成することを前提に組まれているか」を見る軸です。販売管理PJのレビュー待ちは、この軸が未到達のまま実装だけが速くなった結果です。

AI前提では生成量の制約がほぼなくなり、**PJの速度を決めるのは人の確認容量**になります。実装だけが速くなりレビュー待ちが増える状態は、この軸のレベル2未達として現れます。

| レベル | 状態 |
|---|---|
| 未到達 | 従来の工程定義のまま。AIを使うかは個人の裁量 |
| 1 | 個人が自分の作業順序を変えている。WBSと完了条件は従来のまま |
| 2 | PJ計画に、AI適用作業、人の確認点、AI生成物の受入基準を定義している。レビューとテストの処理容量を、AIの生成量に合わせて計画している |
| 3 | 組織標準のAI前提プロセスからPJがテーラリングしている。工程間の成果物がAIの読める形式で受け渡され、人の役割が「承認と例外判断」として定義されている |
| 4 | 工程別の流量、待ち時間、手戻り率のベースラインを持ち、制約工程を数値で検知して要員と自動化を再配分している |
| 5 | 実績から工程構成そのものを再設計し、変更効果を前後比較している |

## AI前提の見積もり・PJ収支

AIの効果と費用が見積もりと収支に反映され、実績で検証されているかを評価します。この軸は、見積もり時点と完了時点の2回、PJ単位で判定します。

平たく言えば、「AIを使うことを、お金の計画に入れているか」を見る軸です。効果（工数の削減）だけでなく、費用（利用料、Skillの保守、確認と修正の工数）も含めます。契約形態（[請負と準委任](../guide/terms.md#契約と収支)）によって、削減した工数が利益になるか売上減になるかが変わるため、効果の帰属を決めることが上位レベルの条件に入ります。

| レベル | 状態 |
|---|---|
| 未到達 | 従来の人月見積もり。AIの効果も費用も反映していない |
| 1 | 担当者が経験で係数を掛けている。AI利用料はPJ原価に入っていない |
| 2 | 見積もりに、AI適用範囲、前提とする成熟度、確認・修正工数、AI利用料、Skill保守費を明示計上している。基準工数を記録し、予実を対比している。顧客契約上のAI利用条件を確認済み |
| 3 | 組織標準の見積もりモデル（成熟度別の係数、費用科目、リスクバッファ）を使っている。削減効果の帰属ルールが契約形態別に定義されている |
| 4 | 見積もりと実績の乖離を統計的に管理し、係数を実績ベースラインから設定している。収支予測を幅で提示できる |
| 5 | 実績から係数と価格モデルを継続更新している。人月以外の価格方式を検証し、標準へ反映している |

**削減効果の帰属ルール**がレベル3の要点です。請負契約では工数削減は利益になりますが、準委任契約では工数削減が売上減につながります。帰属（価格還元、利益、品質への再投資）を決めないまま他の軸を上げると、成熟度が上がるほど収支が悪化するPJが生じます。

**次に読む：** [自動化段階](automation.md)で、A1〜A4の定義と、レベルとの関係を確認します。
