# ai-maturity-assessor

指定リポジトリのAI利用成熟度の**評価下書き**を作る。確定評価ではない。リポジトリで確認できない項目はヒアリング事項として残す。

## 役割分担（厳守）

| 担当 | 行うこと | 行わないこと |
|---|---|---|
| スクリプト | 証拠候補の収集、Git履歴による判定、検証、レベル算定、報告書の生成 | — |
| LLM | 証拠候補が基準を本当に裏付けるかの確認、候補のない基準の証拠探索 | レベルの計算、基準の追加・変更、報告書の数値の書き換え |

レベルと自動化段階は `score_and_render.py` だけが算定する。LLMが「レベル2相当」のような判定を書いてはならない。

## 手順

`<repo>` は評価対象リポジトリの絶対パス。出力先の既定は `<repo>/maturity-out/`（`--out` で変更可）。

### 段1：証拠候補の収集（スクリプト）

```bash
python scripts/collect_evidence.py <repo>
```

`evidence.json` と `findings.draft.json` ができる。下書きの各基準は次のいずれかの状態になる。

| status | 意味 | 段2での扱い |
|---|---|---|
| `met` / `not_met` / `hearing` | スクリプトが確定（Git履歴による判定など） | 変更禁止 |
| `candidate` | 証拠候補あり | 候補を開いて確認し、`met` か、裏付けにならなければ `not_met` / `hearing` にする |
| `unresolved` | 候補なし | リポジトリを探索し、`met` / `not_met` / `hearing` にする |

### 段2：証拠の所在同定（LLM）

`findings.draft.json` を `findings.json` に複写し、`candidate` と `unresolved` をすべて解決する。

- **`met`**：`evidence` に `{"path", "line", "excerpt"}` を1件以上書く。`excerpt` は該当行の文字列をそのまま写す（要約しない）。ファイルの存在だけが証拠の場合は `line` と `excerpt` を `null` にする。
- **`not_met`**：`source` が `repo` の基準だけに使う。`searched` に探索したパスやパターンを書く。
- **`hearing`**：`source` が `hearing` / `either` の基準で、リポジトリ内に証拠がない場合に使う。リポジトリ外に証拠がありうるため `not_met` にはしない。
- 候補がファイル名や単語の一致だけで、基準の内容を裏付けていない場合は `met` にしない。例：`README` に "test" という語があるだけで手順がない場合、`STD-1-01` は `not_met`。
- 判断の補足は `note` に1文で書く。

利用者からヒアリング回答を得た場合は、`evidence` に申告として記録できる（`source` が `repo` の基準には使えない）。

```json
{"attested_by": "回答者", "statement": "回答内容", "where": "証拠の所在（文書名、設定画面など）"}
```

### 段2の検証（スクリプト）

```bash
python scripts/validate_findings.py <repo>
```

exit 0 になるまで `findings.json` を直す。指摘コードの意味は次のとおり。

| コード | 内容 |
|---|---|
| V01 | 基準カタログが収集時から変わった → 段1からやり直す |
| V02 | 基準の欠落・重複・追加 |
| V03 | 未解決の status が残っている |
| V04 | スクリプト確定の判定を変更した |
| V05〜V07 | `met` の証拠がない、ファイルがない、行や抜粋が一致しない |
| V08〜V10 | `not_met` と `hearing` の使い分けの誤り、`searched` の欠落 |
| V11 | 申告の書式不備 |

### 段3：レベル算定と報告書の生成（スクリプト）

```bash
python scripts/score_and_render.py <repo> --project "<PJ名>"
```

`maturity-report.md` と `score.json` ができる。検証に合格していない場合は実行を拒否する。

## 利用者への報告

`maturity-report.md` を提示し、次の3点だけを口頭で添える。報告書の数値を言い換えたり、独自の評価を足したりしない。

1. PJのレベル（確定と暫定上限）と自動化段階
2. 統制不足の有無
3. ヒアリング事項の件数と、制約になっている軸

## 算定規則（参考）

- 軸別レベル：下位レベルを含む全基準が `met` の最上位レベル。**確定**は `met` のみ、**暫定上限**は `hearing` を充足とみなした場合。
- PJのレベル：5軸の最小値。
- 自動化段階：`criteria.json` の `stages` の必須基準で判定する。段階 An はレベル n 以上を前提とする。
- 統制不足：自動化段階が暫定上限をも超える場合は「確定」、確定レベルだけを超える場合は「疑い」。
- レベル4・5はPJ単独では判定しない。

モデルの定義は `references/model.md`、基準の全量は `references/criteria.json` を参照する。基準の追加・変更は `criteria.json` だけで行う。
